# v0.6.128 — Smart Cache и частичные обновления

Готовая сборка включает предыдущую оптимизацию v0.6.127. Этот документ заменяет инструкции о кэше и обновлении из документации v0.6.127; правила запуска Python, одной реплики и восстановления партий остаются прежними.

## Что сделано

- Первый запуск сохраняет HTML, JS, CSS и webmanifest. Иллюстрации и звук сохраняются по мере обращения. Вся коллекция заранее не скачивается.
- При повторном запуске файлы берутся из Cache Storage, затем проверяется манифест. Если изменений нет — никаких окон.
- Сборка определяется SHA-256 содержимого, а не только номером версии. Изменение одного файла при прежнем номере тоже обнаруживается.
- Для обновления скачиваются отсутствующие обязательные файлы и изменившиеся изображения, которые уже были в кэше. Неизменённые файлы используются повторно. Новые, ещё не просмотренные изображения не загружаются заранее.
- Загруженные файлы проверяются по размеру и SHA-256 в сервис-воркере. До успешного завершения рабочая версия сохраняется. Частично скачанные проверенные файлы используются при повторной попытке.
- Окно «Новая версия игры v… / Идёт загрузка обновления...» показывает индикатор и реальное количество подготовленных файлов. Затем появляется «Обновление завершено / Перезагрузите игру, чтобы применить новую версию».
- Перезагрузка выполняется только кнопкой игрока. «Позже» позволяет продолжить партию. Существующие игровые окна не закрываются. Перед перезагрузкой вызывается штатное сохранение соло либо синхронизация и сохранение сетевой сессии; если подтверждение не получено, запрашивается разрешение на рискованную перезагрузку.
- Открытые вкладки закреплены за своими версиями ресурсов. Новый сервис-воркер может обслуживать старую и новую версии по отдельным манифестам. Нет подмены JS посреди партии.
- API партий не попадает в статический кэш. Сохранены авторизация, сетевые ревизии, HTTP 304, gzip и прежняя частота синхронизации.

## Файлы и ограничения кэша

`sw.js` — хранение проверенных файлов по хэшу, подготовка/применение, привязка вкладок, очистка. `update-client.js` и `.css` — окна и диагностика. `asset_manifest.py` — генерация `asset-manifest.json` и идентификатора сборки в HTML. `server.py` — генерация манифеста и проверка совместимости протокола. `network-lobby.js` — сохранение перед обновлением и обработка несовместимого сервера. `map-viewer.js` — обработка протокола. `app.js` — подключение штатного сохранения, удаление дублирующей регистрации SW. `index.html`, `map.html` — подключение нового клиента обновлений. Полный перечень: `CHANGED_FILES_v0.6.128.txt`.

Лимиты Smart Cache: 192 МиБ и 800 файлов; файл больше 20 МиБ не сохраняется при обычном обращении. Удаляются ненужные версии и затем необязательные файлы. Обязательные файлы работающих вкладок и подготовленной версии защищены: при большом числе открытых версий этот лимит может временно превышаться. Старый кэш формата v0.6.126–127 автоматически не стирается, чтобы не повредить ещё работающие старые вкладки; лимит относится к новому хранилищу. Пользовательские сохранения не очищаются.

Если старой вкладке понадобился никогда ранее не сохранённый ресурс, который уже заменён на сервере, несовпадающие байты не подмешиваются: ресурс может быть недоступен до обновления вкладки. При длительной поддержке старых клиентов нужны архивные URL ресурсов на сервере. Офлайн доступны только сохранённые ресурсы; онлайн-партия без сервера не работает.

## Как обновлять через GitHub Desktop

1. Распакуйте сборку и замените файлы проекта. Сохраните партии штатным способом перед серверным деплоем.
2. После своих изменений запускайте `python3 asset_manifest.py`, затем commit и push. Не используйте старый `update_asset_versions.py` как единственный шаг сборки.
3. Python-сервер также автоматически пересоздаёт манифест при старте и запросе манифеста. Поэтому изменение содержимого обнаруживается даже при забытом номере версии. Ему нужны права записи HTML и манифеста в папке приложения. Для read-only публикации заранее сформируйте артефакт и обеспечьте допустимую конфигурацию сервера.
4. Запуск: `python3 server.py`, порт задаётся `PORT`. Dockerfile сохранён. Нужен HTTPS; localhost подходит для разработки. Через `file://` сервис-воркер не работает.
5. При следующем открытии сайта игрок автоматически увидит загрузку изменённых файлов и сам нажмёт «Перезагрузить игру». После перезагрузки используйте существующие «Продолжить»/«Загрузить», если партия не открылась сама.

Публикуйте согласованную сборку целиком, желательно атомарно. При пофайловой загрузке ещё не завершённый деплой может дать ошибку проверки — повторите после завершения. Публичный HTTP без TLS не поддерживает SW.

## Совместимость и перенос хостинга

Кэш использует текущие origin и scope, без адресов Render и внешних облачных API. Подходят Python-сервер на Render, Timeweb, VPS и другие серверы с HTTPS. Сам механизм кэша проверен также с нестандартным префиксом пути в модульном тесте; размещение всей игры под подпапкой отдельно не проверялось, существующие API-маршруты игры рассчитаны на корень сайта.

Прокси не должен кэшировать изменяемые API между пользователями или ставить долгий безусловный кэш на SW/манифест. Сохраняйте ETag, Vary и Cache-Control. Не перекодируйте JS/изображения на CDN: контрольные хэши рассчитаны на исходные байты.

Один Python-процесс/реплика: комнаты по-прежнему в оперативной памяти. Серверный рестарт не стал безопасным постоянным хранилищем. Штатное восстановление использует браузерный снимок, ключ и прежний срок 3 часа. Новый домен/origin получает отдельный кэш и localStorage; автоматического переноса сохранений нет. Перед переносом используйте файл сохранения.

Для будущего несовместимого сетевого протокола измените `protocol` в `asset_manifest.py` и установите серверу `RPG_MIN_CLIENT_PROTOCOL` в требуемое число. Старые запросы получат 426 до изменения партии, клиент покажет обязательное обновление. Сейчас протокол 1; прежние клиенты без заголовка считаются протоколом 1. Не повышайте минимум без соответствующей сборки клиента.

## Проверки

- Браузер: первая установка без окна, повторный запуск без окна, загрузка обновления, повреждённый файл, повторная попытка, явное применение, отсутствие повторного окна, две вкладки со своими версиями. Отдельно проверена замена самого SW.
- В тестовом обновлении загрузились только изменённые `index.html`, `map.html`, `sw.js`, `update-probe.js` и ранее просмотренная `assets/test-used.svg`. Неизменённый `app.js` и непросмотренная `test-unused.svg` не скачивались. Номер 0.6.129 существовал только в одноразовой тестовой копии; итоговый архив — 0.6.128.
- Модульный тест SW: прежний номер с новым содержимым, повреждение, переполнение хранилища, повторная попытка, атомарное применение, перезапуск процесса, восстановление удалённых файлов кэша, потеря связи, обход API, другой origin/scope.
- Серверные проверки: 30 тестов, включая транспорт, авторизацию, протокол 426 и генерацию манифеста; неизменный манифест стабилен, изменение содержимого меняет идентификатор.
- Клиент: один запрос одновременно, отсутствие лишних таймеров, отбрасывание ответа закрытой сессии, сохранение локальных изменений при позднем GET.
- Регрессия: 620 сочетаний эффектов/иммунитетов, 24 варианта зелий, 160 проверок босса, 500 случайных порядков подсказок, масштабирование врагов и лечение паладина.
- Подготовка обновления непосредственно во время партии четырёх игроков прошла без перезагрузки и потери состояния.
- Четыре настоящих клиента в браузерных iframe и отдельная карта: 304 в простое, доставка изменений, имитация потери связи, возврат, сохранение перед перезагрузкой и восстановление партии.

Тесты лежат в `tests-v128`, результаты — в `test-results.json` и логах. `serve_fixture.py` создаёт отдельную копию игры и никогда не должен запускаться против настоящих игроков. Для браузерных сценариев запустите его и откройте указанный URL `/tests-v128/cache.html`, затем `/tests-v128/network.html`.

Сохранена оптимизация v0.6.127: в локальном 10-минутном тесте четырёх игроков и карты HTTP-трафик простоя снизился с 366,99 МБ до 1,67 МБ (99,55%). В последовательности 120 обновлений — на 90,73%. Это конкретные тестовые партии с синтетическим журналом, не гарантия такого же процента для каждого игрового боя. Подробные исходные измерения — `NETWORK_AUDIT_v0.6.127.md`.

## Как проверить самостоятельно

Откройте DevTools → Network и Application → Service Workers / Cache Storage. Первый запуск заполнит обязательные ресурсы. При повторном запуске неизменённые ресурсы должны обслуживаться SW. В консоли: `await RPGUpdates.diagnostics()` — версия клиента, состояние worker, последний серверный манифест, установленные/подготовленные ID, число ресурсов, последние загрузки, обращения к кэшу и ошибки. Списки ограничены 80 записями и обнуляются при перезапуске процесса SW; это диагностика, не постоянная телеметрия. Ручная проверка: `await RPGUpdates.check()`.

На тестовой копии измените один JS/CSS и одну ранее открытую картинку, пересоберите манифест. Не очищайте кэш и localStorage. Должны появиться два последовательных состояния окна, изменённые файлы загрузиться, неизменённые — остаться локальными. Отключите сеть во время следующего обновления, убедитесь в сообщении ошибки и успешной повторной попытке. Повторите с двумя вкладками и активной партией.

## Что не проверялось на реальном оборудовании

Нет заявления о тестах на физических iPhone/Android, Windows, Safari, Яндекс, Edge или установленной PWA. Использованы встроенный браузер и узкое окно 390×844; это не замена реальным устройствам. На устройствах проверьте установку PWA, закрытие/повторное открытие, обновление, кнопки, сенсорную прокрутку и поведение после выгрузки браузера системой. Использованы стандартные SW/Cache Storage/WebCrypto; браузер вправе удалить кэш при нехватке места. После удаления потребуется повторная загрузка.

Не выполнялись реальный деплой на Render/Timeweb, сборка Docker (не установлен), перенос домена, аппаратное закрытие браузера во время скачивания, длительный сетевой стресс и полная ручная партия до финала. Перезапуск SW и сохранность его данных проверены программно. Эти ограничения не скрыты под формулировкой «проверено на всех телефонах».
