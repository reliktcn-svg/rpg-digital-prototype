# v0.6.127 — Network Optimization

Основа: неизменённая рабочая копия v0.6.126. Эта сборка оптимизирует транспорт, кэширование и жизненный цикл сетевых запросов. Правила, баланс, колоды, картинки и расположение интерфейса не менялись.

## Что подтверждено

1. **Полный игровой JSON каждые 400 мс.** `startGameSync()` вызывал синхронизацию 2,5 раза в секунду. GET `/api/rooms/<code>/game` всегда возвращал состояние, даже когда оно не изменялось. Игра проверяла различия только после загрузки всего JSON.
2. **Дополнительный опрос комнаты каждые 900 мс продолжался после начала игры.** Это 1,11 запроса/с на каждого игрока сверх игрового опроса. Он также постоянно переписывал локальный снимок восстановления.
3. **«Карта» запрашивала полный доступный ей снимок каждые 650 мс.** Это отдельная безопасная проекция, не инвентари и скрытые колоды, но она тоже повторялась без изменений.
4. **Сервис-воркер при установке запрашивал 261 путь.** Суммарный размер существующих файлов в этом списке — 282 096 901 байт. Это измерение состава списка и размеров файлов, а не доказательство, что браузер всякий раз скачивал все 282 МБ из Render: часть мог брать HTTP-кэш. При этом для JS/CSS/HTML обычный обработчик явно задавал `no-store`, а новый номер кэша удалял старый кэш приложения.
5. **Собственного gzip для JSON/JS/CSS не было.** Локальные HTTP-ответы были несжатыми. Наличие дополнительного сжатия на стороне Render исторически не проверялось.
6. **Проверять только gameRevision недостаточно.** Способности, инвентарь и торговля могут менять состояние через side-маршруты без повышения основной ревизии. Это подтверждено автоматическим тестом изучения способности.

В коде уже были `clearInterval` и блокировка `syncBusy`: бесконтрольного размножения игровых таймеров при открытии боя не обнаружено. Но опрос лобби не имел защиты от перекрывающихся медленных запросов, а запоздалый ответ старой сессии мог попасть в новую. Это потенциальные гонки, устранённые и проверенные изолированными тестами; связь с конкретным всплеском Render не доказана.

**Почему могли уйти 6,41 ГБ:** постоянные полные снимки плюс крупные загрузки при обновлениях дают достаточный масштаб. Конкретный всплеск 925,31 МБ нельзя точно объяснить без журналов запросов Render. Удалённая статистика хостинга в этой задаче не читалась.

## Что исправлено

- GET состояния и карты поддерживает ETag / If-None-Match: неизменённый ответ — **304 без тела**. Авторизация выполняется до этой проверки.
- ETag построен по полному ответу, включая sideVersions, а не только по номеру хода. Неизменённые сериализованные ответы кэшируются внутри комнаты, отдельно от gameState. Любой POST в комнату инвалидирует обе проекции. Основная игровая ревизия и проверки конфликтов остались прежними.
- При изменении приходит полный актуальный снимок. Поэтому нет цепочек дельт и необходимости восстанавливать пропущенные промежуточные пакеты.
- Клиент сохраняет ETag только принятого ответа. Локальные неподтверждённые действия не затираются фоновым чтением. После записи выполняется сверка с сервером. Поздние ответы закрытой сессии отбрасываются.
- Опрос лобби прекращается после входа в игру. В лобби исключены пересечения опроса и повторная инициализация партии. Игровой таймер остаётся один; первоначальный отложенный запуск также отменяется при замене/выходе.
- Возвращение вкладки и событие восстановления сети вызывают немедленную синхронизацию. Запросы ограничены тайм-аутом 15 секунд, чтобы зависшая сеть не держала блокировку бесконечно. Проверки конфликтов основного состояния не удалены.
- Успешный игровой heartbeat обновляет локальную отметку активности восстановления, даже при 304; запись локального резервного снимка при бездействии ограничена одним разом в минуту.
- JSON и текстовые ресурсы от 512 байт сжимаются gzip при поддержке браузером. Сжатые ответы повторно используются; изображения не перекодируются.
- Статические файлы имеют проверку содержимого ETag и `Cache-Control: no-cache`: это разрешает кэш, но требует проверки актуальности. Неизменённый файл возвращается без тела, изменённый — полностью. HTML также проверяется.
- JS/CSS в index.html и map.html получили индивидуальные хэши содержимого. Неизменённый файл не получает новый URL только из-за нового номера релиза. Скрипт `update_asset_versions.py` обновляет эти ссылки после редактирования.
- Сервис-воркер больше не скачивает всю коллекцию при установке. Он кэширует только реально открытые ресурсы и не подменяет воркер работающей партии принудительно. Офлайн доступны ранее загруженные ресурсы, не вся коллекция заранее.

Интервалы не увеличены: игра — **400 мс**, карта — **650 мс**, лобби до старта — **900 мс**. Полная выдача API остаётся совместимой со старыми клиентами без ETag.

## Измерения HTTP: реальные десять минут

Локальный Python HTTP-сервер; четыре HTTP-клиента игроков и один клиент карты, с прежним расписанием запросов. Фикстура создана настоящим игровым движком: четыре героя, начальные колоды и локации, дополнительно 300 синтетических записей журнала. Её JSON до передачи — 60 225 байт с пробелами Python. Это воспроизводимая нагрузка, не партия реальных пользователей. Каждый прогон длился 600,6 секунды. Учтены тела и заголовки HTTP, **не TCP/TLS**, не загрузки изображений. МБ ниже — десятичные.

| Показатель | v0.6.126 | v0.6.127 |
|---|---:|---:|
| Игровые GET четырёх клиентов | 6 000 | 6 000 |
| GET карты | 924 | 924 |
| Дополнительные GET лобби в игре | 2 668 | 0 |
| Тела игровых ответов | 361,716 МБ | 0,020 МБ |
| Все HTTP-ответы за 10 минут, включая карту | **366,987 МБ** | **1,669 МБ** |
| HTTP 304, игроки / карта | 0 / 0 | 5 996 / 923 |

Сокращение суммарного исходящего HTTP-трафика в этом сценарии — **99,55%**. Четыре первых игровых ответа и первый ответ карты были полными; дальше неизменённые ответы не передавали JSON.

Типичный неизменённый игровой ответ: раньше 60 286 байт тела, теперь **0 байт тела и около 238 байт HTTP-заголовков**. Частота запросов одного игрока после старта снизилась с примерно 3,61/с (игра + комната) до 2,5/с. Частота карты — прежние 1,54/с.

После десятиминутной фазы выполнены **120 настоящих POST изменений состояния и 120 чтений обновлений другим игроком** без искусственных пауз. Ответы изменённых снимков: 7 794 894 → 722 594 байт с заголовками, сокращение **90,73%**. Среднее тело изменённого снимка: 64 767 → 5 701 байт. Это серия действий, а не десятиминутная активная партия; расход за час боя по ней не выдаётся за измеренный.

После добавления серверного кэша сериализованных ответов проведён дополнительный 30-секундный прогон финального транспорта: 300 игровых GET, 47 GET карты, 296/46 ответов 304. Размеры сжатых изменённых ответов совпали. Десятиминутный тест был проведён до этого дополнительного CPU-кэша, уже с теми же ETag/gzip и сетевыми интервалами; результаты трафика сохранены отдельно, не перезаписаны коротким тестом.

Это **линейная оценка по измеренному профилю**, не отдельные 10-минутные нагрузочные тесты на 1 и 10 клиентов. Без отдельного устройства карты:

| Одновременные клиенты игроков | До, МБ / 10 мин | После, МБ / 10 мин |
|---:|---:|---:|
| 1 | 91,229 | 0,362 |
| 4 | 364,916 | 1,448 |
| 10, в нескольких комнатах | 912,289 | 3,621 |

Одна карта в этом тесте добавляла 2,072 МБ раньше и 0,221 МБ теперь. Размеры реальных партий зависят от журнала, предметов и состояния боя.

## Скорость обновлений

В браузерной проверке четыре настоящих клиента в iframe вступили в одну комнату. Для каждой версии выполнены 20 обновлений, измерено время от локального события изменения до появления значения у всех четырёх клиентов:

| | До | После |
|---|---:|---:|
| Среднее | 282 мс | 317 мс |
| Минимум | 158 мс | 157 мс |
| Максимум | 436 мс | 422 мс |

Это короткие локальные серии с разной фазой таймеров, не доказательство ускорения или статистически значимого замедления. Среднее в новой серии оказалось на 35 мс выше; диапазон и максимальная задержка соответствуют прежнему циклу 400 мс плюс обработка. Искусственной задержки не добавлено. Интернет, мобильные сети и реальный Render/Timeweb не измерялись.

## Статические ресурсы

Реальные локальные запросы с Accept-Encoding: gzip:

| Ресурс | Раньше, тело 200 | Теперь, тело 200 | Повтор с новым ETag |
|---|---:|---:|---:|
| app.js | 543 751 Б | 145 202 Б | 304, 0 Б |
| styles.css | 120 147 Б | 26 714 Б | 304, 0 Б |
| Карта PNG | 6 072 366 Б | 6 072 366 Б | 304, 0 Б |
| Тень босса WebP | 336 282 Б | 336 282 Б | 304, 0 Б |

Старый SimpleHTTPRequestHandler умел If-Modified-Since; поэтому нельзя утверждать, что раньше абсолютно все картинки всегда скачивались повторно. В отдельном тесте повторных запросов использовался именно протокол ETag, отсутствовавший в старой версии. Предварительная загрузка 282 МБ теперь отсутствует независимо от этого.

## Проверки и ограничения

- 24 Python-теста транспорта и связанных сценариев: авторизация до 304, side-обновление без main revision, несколько комнат, отдельная карта, gzip, изменение файла с прежним именем, конфликт двух одновременных POST — один 200 и один 409.
- Существующие наборы тестов сервера: территории/покупки, развитие, сброс способностей, босс, выбор усиления врагов — прошли.
- Проверки игрового движка: лечение Паладина, случайный порядок подсказок, усиление врагов, события, экипировка до/во время боя, 620 случаев эффектов врагов, 24 вида зелий, 160 случаев эффектов босса — прошли.
- Изолированные тесты клиентского кода: 304 без применения состояния, side-обновления, локальное действие во время GET, один запрос в полёте, игнорирование ответа старой сессии, один таймер, выход из партии.
- Тест сервис-воркера: отсутствие скачиваний на установке, сохранение HTTP-кэша, правильное клонирование ответа, отсутствие перехвата API, удаление только кэшей игры.
- Реальный браузер: четыре клиента, отдельная карта, серия действий, отсутствие лишнего опроса лобби, 304 при бездействии, имитация потери связи, восстановление, новая страница и продолжение партии.
- Один и два HTTP-клиента покрыты серверными сценариями; четыре — также браузерной и десятиминутной проверкой. Десять — только расчёт. Ограничение шести героев в комнате не менялось.
- Физические iPhone/Android, отдельные приложения Safari/Яндекс, реальные мобильные сети и длительное системное замораживание фоновых вкладок не проверялись. Обработчики возвращения вкладки добавлены; это не заменяет испытание на реальном телефоне.
- Docker в среде отсутствует; Dockerfile проверен чтением, Python-сервер реально запускался с PORT. Развёртывание на Timeweb/Render не выполнялось. В текущей папке нет Git-репозитория; коммит и push не делались.

Исходные результаты и воспроизводимые скрипты находятся в `tests-v127/`. Команда десятиминутного прогона: `python3 tests-v127/benchmark.py /путь/к/сборке 600`. Исходная сборка нужна отдельно для сравнения. Для браузерных проверок запустите server.py и откройте `/tests-v127/browser.html`. Скрипты создают только локальные тестовые партии.

## Перенос на Timeweb

Сборка подготовлена для Docker и PORT. Нужны один экземпляр сервера, HTTPS, порт, health check и корректная передача заголовков кэша. Постоянное хранение комнат **не реализовано**: они остаются в памяти, прежнее восстановление — через снимки браузера. Перезапуск контейнера требует восстановления, новый домен не получает старый localStorage автоматически. Подробнее и команды — в `DEPLOYMENT_v0.6.127.md`. Без отдельной разработки записи комнат в постоянное хранилище нельзя обещать сохранность после любого сбоя.
